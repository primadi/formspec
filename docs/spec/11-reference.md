## 1. Glossary

These terms are **canonical** and binding for all Forma documents and discussions. The hierarchy in one sentence: **Workspace contains Apps, Apps are composed of Modules, Modules contain Resources; data always belongs to the owner of the Workspace where the resource runs.**

| Term | Definition |
|---|---|
| **Workspace** | The umbrella owned by one Data Owner: where data and compute live, the tenant identity across apps, the billing boundary. Has a flag: `dev` (free shared resources, data not guaranteed) or `prod` (dedicated resources, backups, retention). |
| **App** | The unit of deployment and trust boundary. Installed into a Workspace. Composed of Modules. Publishes cross-app interfaces. `kind: App` is the root project manifest. |
| **Module** | A package of code and manifests — static, without tenant or data. Purchased or rented, never "owns" data. Modules are composed into Apps. |
| **Resource** | An Entity, Service, Workflow, etc. inside a Module. The smallest addressable unit. |
| **Tenant** | The representation of a Workspace inside an app's storage — an internal runtime isolation mechanism, not a business concept. One Workspace = the same tenant identity across all its apps. |
| **Data Owner** | = **Workspace Owner** (canonical term): the one identity that owns a workspace — its data, users, grants, compute, and billing. |
| **App Owner** | The vendor of an application (one identity): owns the artifact, versions, and reference seed content. Has no access to production tenant data. |
| **Module Vendor** | = **Module Owner**: the publisher of a module on the marketplace (may be different from the App Owner). |
| **Provider App** | An app whose purpose is to publish a service to other apps. Its vendor is the Workspace Owner of its own workspace. Replaces the concept of "global data." |
| **Grant** | A cross-app access permission: requested by the consumer, approved by the provider's Workspace Owner, recorded, revocable. The metering point for revenue sharing. |
| **Platform Operator** | = **Cloud Owner**: the owner of a Forma Cloud instance — the official Forma Cloud, or an enterprise license holder running their own. |
| **Admin** | An identity with their own key who acts on behalf of an owner via a **delegation certificate** (scope + validity window + revocable). Every admin signature carries the certificate — the audit chain always terminates at the owner. |

### Module vs App — the litmus test

> **Use a Module when *building/composing* — its code goes into your App, its data becomes your Workspace's data.**
> **Use an App when *consuming at runtime* — through a grant to its interface, its data stays in its own Workspace.**

The deciding factor is *can it be deployed independently?* — not "is it used by others?" An App is also used by others, through grants. The common path: start as an App (`forma new` = App); Modules are born by extracting reusable logic, or are purpose-built for the marketplace. One repository may register **both distribution forms** to the registry (the app and its modules, versioned independently).

## 2. Decisions Log

All design decisions that shape the Forma specification. **Final** = committed, implemented in the spec. **Proposed** = in the current draft, awaiting review.

| D2 | OPA/Rego embedded as a Go library inside `forma-control` — the policy engine for governance only, never for business data authorization | Final |
| D3 | Two processes (`forma-control` + `forma-resource`) always, including development. The old term "Single-Binary" is renamed to "Forma Standalone" — meaning self-contained deployment without cloud dependencies, not one process | Final |
| D4 | Plane names: Control Plane & Resource Plane. Binary names: `forma-control` & `forma-resource` | Final |
| D5 | Six `ctx.*` primitives as a **closed set**; users may not define custom infrastructure services | Final |
| D6 | Sidecar trust model = native. Identity proxy and Signed Query Registry protections apply equally to all languages | Final |
| D7 | Sub-tenants managed as a business module (`forma/tenant-billing`) in the Resource Plane, not in the Control Plane. The term "sub-tenant" is no longer used | Final |
| D8 | **Licensing:** spec = CC0. `forma-resource` & `forma-control` = FSL (Functional Source License) — source available, free for any commercial application, prohibited from being sold as a competing managed service. Each version automatically becomes Apache 2.0 after 2 years. Enterprise governance features gated by a license token. Applied from day one — no mid-stream relicense. Communication position: "fair source," not an OSI "open source" claim | Final |
| D9 | Working language for documents: Indonesian (personal project). Public spec: English | Final |
| D10 | Features adopted from Frappe (form layout hints, print formats, approval-in-state-machine) and PocketBase (realtime subscription convention, instant admin panel) are **core scope**, not an optional backlog | Final |
| D11 | **Non-license structural defenses:** "Forma" trademark registered from the start. Module registry + Verified Badge (ed25519 trust chain) operated as a centralized official hub. Control Plane governance and locale modules (`forma/locale-id`) as service moats that cannot be forked | Final |
| D12 | Scheduler, mail, notification, and seeder/factory are **official modules** built on top of primitives (mail → `ctx.queue`, notify → `ctx.pubsub`), not new primitives. The `ctx.*` closed set stays at six | Final |
| D13 | REPL (`forma repl`, Starlark-based with `ctx.*` access) is a **first-class feature**, including as a surface for Forma Agent Skills for AI debugging | Final |
| D14 | Frontend is described as YAML spec with `kind` patterns (K8s-style). The entire project has only three file types: `yaml`, `script`, `asset`. Frontend kinds are limited to patterned UI; arbitrary UI uses the explicit `asset` escape hatch | Final |
| D15 | Positioning: Laravel (and others) = sources of inspiration with explicit reasons, not scope boundaries. Forma = a synthesis of six sources. "The Laravel of Go" is only a communication bridge | Final |
| D16 | The canonical example: **Order-to-Cash** (the old companion rewritten to follow the new spec), with a "without Forma vs with Forma" two-column narrative format, used in all public documents | Final |
| D17 | **Concern → Kind map** (Appendix B / §4 of this document): the kind catalog is determined per concern, with the principle of *derived by default* — CRUD API, admin panel, and docs are born automatically from Entity; exposure/UI kinds (`Api`, `Form`, etc.) exist only to override | Final |
| D18 | **Kind extensible in three layers:** spec built-ins (`Module, Entity, Service, Config, Migration`) → official modules via `KindDefinition` (CRD-like: `Seed, Schedule, MailTemplate, …`) → third-party modules (namespaced, subject to Verified Badge). Guardrail: application developers almost never define kinds — needing a new kind means extending the framework; in 95% of cases the answer is `Entity` | Final |
| D19 | **`kind: Module` design:** `metadata.name` = identity AND permission namespace (no alias). Vendor path for registry/dependency resolution. Contents discovered via scanning, not listed. Module-level config defaults. **No** additional permission block | Final |
| D20 | **Explicit permission model for all five impl types:** every action declares `required_permission` (caller guard) and `uses` (code's own access: db tier, other resources, primitives). Grants are never derived from usage. Runtime enforcement via identity proxy for all types. Auto-scan scripts only as an honesty verifier (`forma validate`). Module footprint = aggregate of declarations, presented as consent at install time. `ctx.auth.has()` may only reference declared permissions | Final |
| D21 | **Two app distribution models:** (A) self-managed tenancy — the developer manages multi-tenancy themselves, must remain supported (FSL credibility, extreme density cases). (B) **platform-managed tenancy — the recommended default path**: apps are written tenancy-blind, Forma Cloud decides topology (isolated instances or pooled via the same `tenant_id` machine). Role separation: **App Owner** (artifact, versions, sanitized metrics — no tenant data access) vs **Data Owner** (users, data, backup, consent footprint per D20, re-consent on footprint changes). Support access = impersonation grant from the Data Owner, time-boxed, audited | Final |
| D22 | **Marketplace + revenue sharing** as an ecosystem pillar. The declarative dependency graph (`depends`) = the basis for cross-owner module usage metering. **Commercial terms (price, revenue share) live in the registry, not in the manifest** — the manifest remains purely technical. The same module can be free self-hosted and paid on the marketplace without YAML changes | Final |
| D23 | **Tenancy in the manifest = semantics only; isolation strategy is total.** Every Entity is **tenant-isolated by default, without exception and without implicit derivation**. Global/reference data is an explicit exception: `tenant.isolated: false` is only valid if `characteristics: [reference]` (validated). Ownership follows: reference entity data is owned by the **App Owner** (shipped/updated via app releases/seeds; Data Owner is read-only); tenant-isolated data is owned by the **Data Owner**. The entire strategy/topology (single/multi, pooled/isolated, tiering) is not an app spec concern — it is decided at deployment time (D21) | Final |
| D24 | **Manifests are never encrypted** — readability is a feature (consent D20, `forma validate`, diff review, AI). Protection of commercial module value: (1) real IP may be binary via `impl` native/compiled without source, (2) signed vendor provenance (ed25519, D11) + "Verified-only" policy in the Control Plane — a renamed copy cannot forge the signature and cannot enter the marketplace or a governed environment, (3) the economics of update + support + liability do not transfer with a copy, (4) legal protection via module license | Final |
| D25 | **App as a first-class layer**: Workspace → App → Module → Resource. App = unit of deployment, trust boundary, and interface publication (`kind: App`, root project). Module = static code packaging without tenant/data. Default private — cross-app access only via publish → request → **grant approved by the Data Owner**, recorded, revocable, and the metering point for revenue sharing (D22) | Final |
| D26 | **No global storage at all** (replacing the `isolated: false` mechanism of D23): `characteristics: reference` remains as a domain marker (read-only for Data Owner, seeded). Small/stable lookups → seeded per-tenant by the App Owner via releases. Live/large data (exchange rates, ICD-10) → a **provider app** owned by the vendor, publishing a service | Final |
| D27 | **Ownership follows the workspace where the resource runs** — one rule for all cases. A purchased/rented module never owns the data. Compute = the Data Owner's responsibility. Expired license → module **degraded to read-only**: actions/services stop, but `list/find/export/backup` **can never be license-gated, without expiry** — normatively guaranteed at runtime (the license token refuses to gate standard read operations) | Final |
| D28 | **Canonical glossary** (Appendix C / §1 of this document) is binding for all documents and discussions: Workspace, App, Module, Resource, Tenant, Data Owner, App Owner, Module Vendor, Provider App, Grant, Platform Operator, Admin | Final |
| D29 | **Workspace = the one and only multi-tenancy model in Forma** (amendment to D21: the self-managed tenancy path inside an app is removed; D7: the term sub-tenant is no longer used). Applications are 100% tenancy-blind. `FORMA_TENANCY` is removed. Large tenants wanting their own servers → enterprise license → run their own Forma Cloud as Platform Operator. The workspace primitive exists in all tiers (including Standalone — needed even for dev). What is paid for is the *management plane* at scale (automated provisioning, billing, marketplace) | Final |
| D30 | **Contract integrity (grants, consents, licenses, metering) via a transparency log. Blockchain is rejected.** Mechanism: (1) audit store = append-only Merkle tree with inclusion proofs, (2) every contract is signed by both parties (ed25519), cryptographically non-repudiable, (3) root checkpoints are published/mirrored outside the operator's control. Blockchain solves a problem Forma does not have (consensus without a central authority — when the Control Plane is the central authority by design and the centralized registry is the D11 moat). Re-evaluated only if multi-operator federation materializes (Q19) | Final |
| D31 | **Credible Exit Guarantee** — the operator does not need to be trusted because leaving is cheap, enforced by the market, not by a chain. Four normative guarantees in the spec: (1) self-custodied identity — workspace/app/vendor keys are held by their owners, the platform stores only public keys, (2) contracts = portable documents signed by two parties, copies held by each + inclusion proof — verifiable by a new operator without the old operator's cooperation (the D8 license token is already portable by design), (3) backup/export format is normative in the open spec — any conforming implementation can restore, combined with D27 (export is never license-gated), (4) log checkpoints mirrored by third parties (D30). Honest positioning: *a verifiable, easy-to-leave centralized operator* — not trustless | Final |
| D32 | **Idempotency & concurrency enforced by the framework**: (1) `idempotent: true` is enforced at runtime via an **idempotency store** `(tenant, action, key) → pending|completed + stored response` — a duplicate after completion **replays the original response** (a webhook retry gets its 200 again), a duplicate while pending → wait/409. Key from the client (`Idempotency-Key` header/field — webhooks, outbox) or **server-issued via a prepare-step** (double-submit form create). Retention via expiry, not delete-on-commit. Handlers may still check manually. (2) The `version` column (Core Basic §19) carries **optimistic concurrency** semantics: CAS on update, mismatch → 409 + current version, default active for all Entities. (3) `last_updated`/`updated_at` = pure audit metadata, written by the DB, **never** used as a comparison token (fragile: clock resolution, NTP, non-monotonic) | Final |
| D33 | **The declarative vs imperative line — a three-question litmus test**: (1) facts/guarantees the framework enforces → YAML; sequential procedures → handler; (2) **YAML vocabulary = closed set** — never add syntax per business case; escape hatch = Starlark expressions inside existing constructs (guard, conditions) — *declared location, scripted expression*; (3) consequences of an event → `deliver` (declarative); steps within an action → handler. Concrete consequence: **`channel: queue` added to `deliver`** (email/WA/PDF = consequences of the `paid` event, not steps of mark-paid) | Final |
| D34 | **Spec tooling ladder** (the answer to verbosity): (1) JSON Schema per kind published at forma.dev/schemas + LSP — autocomplete, hover docs, realtime validation; nearly free thanks to the `apiVersion/kind` format; (2) scaffold CLI `forma new <kind>`; (3) visual editor in the admin panel à la Frappe's DocType editor — **writes YAML to files/PRs, not to a hidden DB; git remains the source of truth**; (4) Agent Skill = spec editor for AI. Never a proprietary binary format | Final |
| D35 | **`kind: Subscription` (Core Basic)** — subscribe to another resource's events from the consuming module, without touching the publisher's manifest. A structural prerequisite for the module ecosystem (signed modules cannot be edited). The `deliver` vocabulary is identical (closed set, D33). **The dividing line = ownership of the guarantee**: consequences that are the publisher's contract (journal entries ← billing's promise) stay in the publisher's `deliver`. Optional/third-party/late-born reactions → Subscription. Anti-scatter guard: (1) fan-out is always compiled — `forma describe` and the admin panel show the merged deliver + all Subscriptions pointing to it, (2) Subscriptions enter the consent footprint at install (D20), (3) the durability contract remains two-sided. Symmetry: cross-module = install consent; cross-app = grant (D25) | Final |
| D36 | **Frontend architecture** (v0.5.0 — expanded from 9 to 12 kinds): (1) **interpretive renderer** — SPA shell reads manifests via meta API, not codegen UI; the renderer is also **embeddable as a library** (`<FormaPage/>` in an existing React app — two-way adoption); (2) **component contract** = ES module `mount(el, props, forma)` framework-agnostic + client `forma.api` (runs as the logged-in user) + **`forma.ui`** standard services (toast/dialog/confirm/drawer) + closed base component library + scoped CSS + CSP; full-custom page = Page containing a single component; (3) **the language line**: declarative expressions = **FormaExpr** (Starlark expression subset, small JS AST interpreter, one grammar with server-side guards, UX-only) with a closed behavior vocabulary `visible_when/readonly_when/required_when/compute` (reactive); imperative code = JS/TS via components — full Starlark in the browser is rejected; (4) realtime convention `entity:{module}.{name}` with per-message permission filtering; (5) **`kind: Print`** — multi-target output (pdf/thermal/dotmatrix/html) with per-format pipeline; (6) **`kind: Theme`** — tokens + CSS layer + widget skins, packaged in modules, signed, sold on the marketplace, selected per workspace by the Data Owner; (7) **`kind: Dashboard`** + **`kind: Widget`** — widget catalog (visibility derived from permissions) + customizable dashboards (*manifests define what is possible, preferences record what is chosen*); **`kind: Report`** — parameterized reports + groups + totals + async export; (8) **Transfer manager** (`forma.files` + upload/download tray) = renderer infrastructure, not a kind; (9) **Hybrid Low-Code** — 80/20 split with Design-Time Layout Locking (modal vs drawer vs separate_page decided at design time in the manifest); (10) **`kind: Wizard`** (v0.5.0) — multi-step business process with stepper, depends_on, partial save, composite action; **`kind: Kanban`** (v0.5.0) — drag-and-drop status board with optimistic update + CAS version; **`kind: Timeline`** (v0.5.0) — chronological append-only event journal with date grouping + infinite scroll. Twelve kinds total | Final |
| D37 | **Workspace identity, per-app membership**: user identity = workspace level (one account per human — prerequisite for cross-app grants, audit, SSO). Membership + role assignment = per-app (`forma.core` + `app-membership` entity). The user population of each app may be completely different within one workspace. Role definitions remain owned by modules → automatically per-app | Final |
| D38 | **Task/page-based authorization = an administration layer, not enforcement.** Implicit page-based authority ("can see page → implicitly can save its entity") is **rejected**: UI provenance cannot be verified server-side (confused deputy) — and unmanaged clients (Flutter/API) never pass through a page at all. Instead: every Page has a **derived capability footprint** from its composition (Form → actions, Table → list, component → explicit `needs:` declaration). Admin grants role access per-page → the footprint is **materialized** into real permission resources, visible in `forma describe page`, auditable. Enforcement is always at the resource (D20). Complements: headless form engine `forma.form()` for full JS control; unmanaged mobile (Flutter) = first-class API consumer today (HTTP+WS+codegen Dart/TS); multi-entity wizard → composite action server-side for atomicity | Final |
| D39 | **Control Plane architecture**: (1) `kind: Policy` = **structured YAML + Rego escape hatch** (the D33 pattern, governance edition; structured keys compile to Rego — one engine, one decision log); policy floor cannot be disabled: no self-approval, no unsigned artifact in non-dev, no environment override; (2) **two key classes**: owner keys self-custodied (Control stores public keys only) vs platform keys in HSM/KMS; (3) **single contract model** for grants/consents/licenses — portable documents signed by two parties + Merkle inclusion proof + published checkpoints (D30/D31); license tokens cannot gate list/find/export/backup (floor D27); (4) **consent delta = approval**: a new version's footprint change blocks deployment until the Data Owner re-consents; (5) **REPL governance**: dev = full, staging = read-write audited, production = read-only default + write requires time-boxed approval + session enters the transparency log; (6) impersonation only via a signed, time-boxed Data Owner grant — no operator backdoor | Final |
| D40 | **Actor & ownership model**: four symmetric owners — **Workspace Owner** (alias Data Owner), **App Owner**, **Module Owner** (alias Module Vendor), **Cloud Owner** (alias Platform Operator). One identity may hold several roles. **Owner = exactly one identity** (email + self-custodied owner key). **Admin via delegation certificate**: admin has their own key + a delegation certificate signed by the owner (scope, validity, revocable) — every admin signature carries the certificate, the cryptographic chain always terminates at the owner. Owner-only (non-delegable): accept/relinquish ownership, issue/revoke delegations, rotate owner key. **Two-path transfer**: consensual (two signatures, Cloud Owner facilitates & records — does not grant) and recovery (operator-mediated with normative due process: re-attestation, waiting period, notification to all admins, public transparency-log entry) — unilateral transfer by the operator = backdoor, rejected | Final |
| D41 | **Governance of backup/restore**: only **workspace data** needs customizable backup (the only thing not reproducible) — governed by the Workspace Owner: schedule, retention, scope, **external target owned by the owner** (the living form of Credible Exit — a daily copy in the owner's hands; never license-gated per D27). App/module artifacts = reproducible from git + registry (no separate backup; registry retention = Cloud). Contracts/logs/membership = Cloud Owner + each party's own contract copies (D31). Infra durability = Cloud SLA. Rules: `backup create` is delegable; **`restore` that overwrites requires the owner's signature or an explicit `backup.restore`-scoped delegation + transparency log**. Per-tenant encryption with an owner-supplied key option. Point-in-time consistency per app; cross-app is near-point-in-time + outbox reconciliation post-restore | Final |
| D42 | **Marketplace & economic model**: (1) **one marketplace** — module/app/theme/widget = category listings in one infrastructure (all are signed artifacts in the registry). Commercial terms in the listing, never in the manifest (D22). (2) **Closed pricing vocabulary**: free · one_time · subscription · per_seat (← membership D37) · per_call (← grant metering D25) · per_transaction (← metering event count-only, Control never reads payload) · metered_passthrough. (3) **Verifiable metering**: counts signed by the Resource Plane + anchored in the transparency log (D30) — the vendor verifies their sales, the Workspace Owner verifies their invoice, both against the operator. (4) **One ledger per owner**: debit (infra, subscriptions) + credit (payout, top-up); income offsets charges. Settlement: **prepaid default** (local top-up; balance exhausted → grace → read-only degradation D27) + **postpaid trust tier** (invoice/PO enterprise). (5) **Many license types** (trial/perpetual/subscription/usage — all resolve to a D8 license token with type & validity) vs **one uniform infra metering type** — two lines on one invoice. (6) **Transparent scaling**: mechanics are never in the app spec (consequence of D29 + location transparency). The owner sets the resource plan + **budget cap** (prepaid = natural brake), the operator turns the knobs. Per tier: managed autoscale / BYOI / self-hosted manual. (7) Fixed guardrails: read-only degradation + export never gated (D27), Verified Badge mandatory for paid listings (D11), token portable & air-gap safe (D8), free/self-hosted FSL path intact | Final |
| D43 | **Official consoles = mandatory dogfooding**: three Forma apps per persona — `forma/console` (Workspace Owner + admin), `forma/studio` (App/Module Owner — creator), `forma/ops` (Cloud Owner + admin). Consoles = permanent proving ground for the spec. Architecture: consoles run on the ops workspace's Resource Plane; Control Plane access via a bridge `kind: Service` (the "Control never executes business logic" prohibition remains intact). Owner key signing = **client-side** (custom component + WebCrypto — self-custodied keys per D31 never touch the server). **Bedrock exception**: the `forma-ctl` emergency CLI = conventional code inside the `forma-control` binary, never depending on the platform it repairs. The web console = convenience, not the only path. Documentation = the console apps' own YAML manifests + one architecture note | Final |
| D44 | **Non-technical owner principle** — a Workspace Owner may be a business owner who is not technical. Their mandatory activities are minimal: (1) **owner key = passkey (WebAuthn) as the default form** — private key in the device secure enclave (iCloud/Google sync = answer to lost phone), platform stores public key only: D31 intact, UX = "login with fingerprint." The contract hash is bound into the assertion challenge → signing = notification + tap + biometric. Raw ed25519 via CLI remains for power users — **two signature envelopes, one contract model**; (2) **owner obligations locked to the minimum**: approve consent/footprint-delta/grant/billing-above-threshold/restore/admin-appointment/transfer — the rest is delegation (D40), including the software-house pattern as certificate-scoped admin (scoped, audited, revocable with one tap); (3) **consent screen MUST be in plain human language** with expandable technical detail — a normative requirement; (4) anti-fatigue: prepaid top-up = billing approval itself, budget cap = auto-approve within it (D42) | Final |
| D45 | **No unmanaged storage in a workspace**: data outside `ctx.*` primitives = silently exits all guarantees (backup D41, Credible Exit D31, export D27, isolation, consent D20) — "Forma module" is a promise. The official ladder for advanced needs: (1) `ctx.db` raw SQL (already exists), (2) **module-owned tables via `kind: Migration`** — free structure, but **must have a `tenant_id` column** and live in their category schema (still backed up/isolated/audited), (3) exotic engines (search/vector/graph) → provider app owned by the vendor or wrapped as `kind: Service`. The Workspace Owner **never** provides raw storage for modules (BYOI = managed primitives in the owner's infra, not raw access). **Sidecars must be stateless**: ephemeral scratch disk allowed, persistent state only via `ctx.*` | Final |
| D46 | **Layered defense for `ctx.db` & binary handlers** (scenario: a malicious free native module targeting GL data): (1) db scope **default = own module**; cross-module must be declared → appears in consent; **cross-module write = high-risk consent** (different presentation); (2) runtime violations are normatively defined: undeclared access → blocked + alert + **module auto-suspended** + incident audit — even checking for the existence of data triggers this; (3) **honest acknowledgment**: native enforcement = best-effort (in-process full trust, credentials are brokered but memory can be inspected) — the law of nature for all binary plugins. The real defense = **provenance: impl type gated by trust tier** — unverified/free: only sandbox (script/script_ref/WASM); Verified Badge: + sidecar (proxy-isolated); Verified + security scan + layered approval: + native; (4) blast radius: tenant injection at the ctx layer limits damage to the consenting workspace; recovery via audit + D41 external backup | Final |
| D47 | **Two-channel inter-plane model** (Plane Protocol v0.1.0) — sharpens the "no write-back" rule: (1) **desired-state channel** (Control→Resource, pull-only): signed, monotonically-versioned snapshot (rollback attack protection) containing policy, desired deployments, trust anchors, grants, revocations, membership; the Resource can never mutate governance state; (2) **evidence channel** (Resource→Control, append-only): deploy status, metering (count-only), audit anchor (Merkle root of local segment — ties workspace audit into the transparency log without shipping contents), violation incidents — evidence can be appended, never edited, all anchored in the log (evidence about the operator is tamper-evident too). Without this channel, verifiable metering D42 and D46 incidents have no path. Outage: serve-forever on last snapshot + local refusal of high-governance operations past threshold; fail-closed on unknown trust/major-version constructs | Final |
| D48 | **Core Extended v0.2.0** — three new kinds + normatization of stubs: (1) **`kind: Workflow`** (closes Q8/D10): approval attaches to a state-machine transition without modifying the Entity (the D35 pattern); sequential quorum-based steps + guard, no self-approval (the D39 floor lifted to business workflows), visible in `forma describe` merged output; (2) **`kind: Api`**: exposure override (path/version/disable/external gRPC) — surface never widens access beyond `expose`; (3) **`kind: KindDefinition`** (answers Q14): namespacing via **apiVersion group à la CRD** (`seed.forma.dev/v1`) — collisions structurally impossible, handler runs under the module's `uses`, schema automatically feeds LSP (D34); (4) **`kind: Webhook` & `kind: Mockup`** normatized from stubs + environment binding is config-driven (business handlers never branch on environment; `mock_enabled` per env) + state & fault-injection mockups; (5) Tier-2 streaming folded into `kind: Subscription` (D35) — **dynamic subscriptions = data, not manifest**; (6) notification/registry/control content moved to their new homes (forma/notify, marketplace, Control Spec) | Final |
| D49 | **API exposure is deny-by-default. `spec.expose` is the opt-in gate.** No external endpoint is created unless the entity declares `spec.expose` with at least one protocol type. `kind: Api` (D48) only overrides presentation for already-exposed surfaces — it cannot create access. This minimizes attack surface and forces deliberate exposure decisions per entity per protocol. Internal callers (same-process services, Starlark scripts, events) are unaffected | Final |
| D50 | **Multi-protocol router with workspace slug prefix and smart internal dispatch.** (1) The router MUST use a radix-tree or equivalent O(path segments) lookup — route count must not linearly degrade performance. (2) Every external route is prefixed with `/{workspace_slug}/api/...` — slug is a human-readable Workspace alias with UUID fallback. (3) Internal callers (same process, registry-local) bypass the network → direct function dispatch, no serialization overhead. Cross-process callers use the configured protocol adapter (REST/gRPC/WS). (4) Route descriptors are protocol-agnostic; the router dispatches to the correct protocol adapter | Final |

A completeness checklist. Every Laravel feature that has not been mapped must enter this table with one of three statuses: *Counterpart*, *Deliberately Different + reason*, or *Gap (→ Open Question)*.

## 4. Concern → Kind Catalog

Three catalog principles:
1. **Derived by default, kind to override.** CRUD API, admin panel, and docs are born automatically from `Entity`. Exposure/UI kinds exist only to deviate from defaults. Granularity: one kind per concern-unit, not per screen (`Form` with `spec.mode`, not `EntityCreateUI`).
2. **Kinds extensible in three layers** (D18): spec built-ins → official modules via `KindDefinition` → third-party (namespaced + Verified Badge).
3. **Data is not a manifest.** General Ledger = an *instance* of `kind: Module`; account "1-1001 Cash" = a database row (runtime Entity instance), not a manifest.

| # | Concern | Kind | Location |
|---|---|---|---|
| 1 | Packaging | `Module`, `App` | Core Basic |
| 2 | Domain model | `Entity`, `Service` | Core Basic |
| 3 | Business processes | State machine inline in Entity; `Workflow` for approval/cross-role (D10 container) | Extended |
| 4 | Configuration | `Config` | Core Basic |
| 5 | Exposure / API | Derived by default; `Api` (override REST/external gRPC), `Webhook` (inbound) | Extended |
| 6 | UI / Frontend | Derived by default; `Page`, `Form`, `Table`, `Dashboard`, `Widget`, `Report`, `Menu`, `Print`, `Theme` | Frontend Spec |
| 7 | Data lifecycle | `Migration` (custom DDL only; structural derived from Entity diffs) | Core Basic |
| 8 | Seeding / testing | `Seed`, `Factory` | Module `forma/seed` |
| 9 | Async / communication | `Schedule`, `MailTemplate`, `NotificationChannel` | Respective official modules |
| 10 | External integration | Wrapped as `Service`; `Mockup` for third-party simulation | Extended |
| 11 | Governance | `Environment`, `Policy` (Rego) | Control Spec |
| 12 | Cross-module reactions to events | `Subscription` (D35) — same `deliver` vocabulary as publisher | Core Basic |

## 5. Admin Layers

Admin roles **inside** a business application are not platform personas — they are the bottom layer, whose mechanism is already complete:

| Layer | Example (clinic app) | Mechanism | UI |
|---|---|---|---|
| **L1 — in-app admin** | Clinic admin manages doctor/cashier users & roles | Standard RBAC: module roles (D19) with `core.members.*` permissions over the forma.core entity, scoped per app (D37) | The app's own UI — derived admin panel over forma.core. The developer never builds user management. |
| **L2 — Workspace Owner + admin** | Clinic owner | D40 (single owner + delegation cert); install, consent, grant, backup (D41), billing (D42) | `forma/console` |
| **L3 — App/Module Owner + admin** | Vendor of the clinic app; or a workspace owner building their own internal app (dual L2+L3, no marketplace) | D40, releases & listings (D42) | `forma/studio` + CLI |
| **L4 — Cloud Owner + admin** | Forma Cloud operator | D40 + Control Spec; emergency path = bedrock `forma-ctl` (D43) | `forma/ops` |

Documentation for L2–L4 console features = the consoles' own YAML manifests (D14/D43) + one architecture note. L1 needs no document — it is a normal usage pattern, demonstrated in the Companion.
