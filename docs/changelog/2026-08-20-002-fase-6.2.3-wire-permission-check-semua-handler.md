# 2026-08-20-002 — Fase 6.2.3: Wire Permission Check ke Semua Handler (Kedua Surface)

## Apa yang diubah

Melengkapi enforcement permission di kedua surface API. Enforcement inti
(`RequirePermission` + `Identity.HasPermission`) sudah ter-wire di semua route
(standard CRUD, custom action, prepare) via `registerRoute`/`registerRouteWithPattern`
— setiap route membawa `RequiredPermission` (`{module}.{plural}.{action}`).
Gap yang ditutup di sini: **perilaku 404 vs 403 sesuai spec**.

### Surface-aware 404 (spec frontend/04 §4)

- `RequirePermission` kini membedakan surface:
  - **UI surface (`/_ui/`)** + permission entity **list/view** tanpa izin →
    **404 NOT_FOUND** (keberadaan entity tidak bocor ke caller yang tidak berhak).
  - Selain itu (external `/api/v1/`, atau action non-list/view) → **403 FORBIDDEN**.
- Helper `isUISurface(path)` + `isEntityVisibilityPerm(perm)`.

### Test enforcement

- `internal/api/permission_enforcement_test.go` — memverifikasi:
  - UI entity list tanpa list/view → 404
  - External entity list tanpa list/view → 403
  - UI entity list dengan list → 200
  - UI entity create tanpa create → 403 (bukan 404)
  - Tanpa token → 401
- `GetAuthValidator()` (getter) + test me-restore validator global di cleanup
  (mencegah test enforcement merusak test WebSocket yang bergantung dev fallback).

## Kenapa diubah

Spec `frontend/04-spec-resolution-api.md` §4 mengontrakkan: entity → 404 kalau
caller tidak punya permission list/view (bukan 403), supaya keberadaan entity
tidak bocor. Sebelumnya `RequirePermission` selalu 403 di kedua surface.
