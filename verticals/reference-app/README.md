# reference-app — dev-mode composition of every vertical

**Not the production path.** This folder demonstrates all of `verticals/*` running
together with one frontend, by aggregating each independent App's manifests into
one `spec/` tree at dev time — the same shortcut every other example in this repo
already relies on (`resource.New(cfg)` reads exactly one `SpecPath`; see
[`docs/spec/02-core-basic.md`](../../docs/spec/02-core-basic.md) §6.0, which itself
calls direct-filesystem loading "non-conformant").

The real production path is per-App `formspec apply` into one workspace (§6.0's
two-stage Registration/Deployment pipeline), which is what makes cross-app
`consumes`/`publishes` grants meaningful. That path can't yet *serve* a converged
multi-App workspace end-to-end — the Resource Plane's SyncAgent registry sync
isn't wired to the live HTTP router yet (`docs/runtimes/02-formspec-resource.md:138`).
See [`docs/architecture/07-vertical-modules.md`](../../docs/architecture/07-vertical-modules.md)
for the full gap list. This folder exists so the composition can still be
*demonstrated* today, honestly labeled as a dev convenience.

## Usage

```sh
./compose.sh
go run ../../examples/reference-app --spec ./spec --dsn sqlite:.formspec/data.db
```

`compose.sh` copies each vertical's `spec/modules/<name>/` (and, for `inventory`/`gl`,
their App-level menus/widgets/reports/tables/dashboards, namespaced per app to avoid
path collisions like both shipping their own `config/app.yaml`) into `spec/modules/`
and `spec/_app-extras/` here. Both are gitignored and regenerated by the script —
never hand-edit them; edit the source vertical instead and re-run `compose.sh`.

The only content that belongs to `reference-app` itself: `spec/formspec.yaml`,
`spec/config/app.yaml` (a merge of each vertical's own app-level config keys), and
`spec/dashboards/erp-overview.yaml` — one small cross-module dashboard (billing
revenue + inventory stock in one view) proving the composition actually works
end-to-end. No new wizards or per-module UI are added here — those stay with the
module that owns them, or are deferred along with the rest of the roadmap.
